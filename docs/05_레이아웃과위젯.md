# 05. 레이아웃과 위젯 (Page · Bento · Widget 설계)

> 본 문서는 ERP No-Code 빌더 프로젝트의 **참조 문서**이다. 상위 원칙·규칙·색인은 「프로젝트 지침」·「01. 규칙과 구조」를 따른다.
> 본 문서는 **화면 배치의 데이터 계약(LayoutSpec)과 Widget 층**을 설계한다 — *코드 착수 전 계약*. `FieldSpec`이 폼의 진실이듯, `LayoutSpec`이 페이지 배치의 진실이다.
> 상태: **설계(구현 전)**. 값(ROW_UNIT·캡 폭 등)은 잠정, 구조·계약은 확정 대상.

---

## 0. 핵심 원리 — 모델 먼저

이 시스템의 헌법(1번)은 "도메인은 직렬화 데이터로만 들어온다"이다. 화면 배치도 예외가 아니다. 위젯 편집기의 **진짜 산출물은 편집기 UI가 아니라 `LayoutSpec`** — 직렬화 가능한 페이지 배치 계약이다.

```
편집기(사람) ─┐
LLM(자연어)  ─┼─→  LayoutSpec  ─→  Bento 런타임 렌더러 ─→ 화면
런타임(불러옴) ┘   (단일 진실)
```

셋(편집기·LLM·런타임)이 **한 모델의 생산자/소비자**다. 모델이 맞으면 나머지는 그 함수이고, 모델이 틀리면 셋 다 틀린다. 그래서 UI(편집기)가 아니라 **계약(LayoutSpec)부터** 설계한다. (목업은 모델이 0개라 그대로 코드화하면 모델을 암묵적·잘못 굳힌다 — 그 함정을 피하는 게 본 문서의 목적.)

## 1. LayoutSpec 계약 (설계의 80%)

### 1-1. shape

```ts
type PageSpec = {
  header: { title: string; tabs?: Tab[]; primaryAction?: ActionRef };  // 제목·탭·CTA 하나 (설명 없음)
  bento: { widgets: WidgetInstance[] };
};

type WidgetInstance = {
  id: string;
  type: WidgetType;                 // 'ListWidget' | 'StatWidget' | ... (닫힌 레지스트리)
  x: number; y: number;             // 격자 좌표(1-indexed): 시작 열 1~12, 시작 행 1~3
  w: number; h: number;             // footprint: w ∈ {2,3,4,6,12}, h ∈ {1,2,3} (타입별 부분집합)
  config: unknown;                  // 도메인 — 위젯 타입별 스키마(함수 금지, key 참조만)
};
```

### 1-2. 좌표 모델 (확정 — 명시 좌표 · 무 reflow)

- **명시 2D 좌표** `x,y,w,h`. 세로줄에 높이 다른 위젯(예: 좌 6×3 차트 + 우 6×1 + 6×2)이 표현된다.
- **중력·compaction·reflow 없음.** 저작자가 놓은 좌표 그대로 렌더. (편집 ≠ 사용 — 저작은 별도 단계라 라이브 홈화면식 재배치가 불필요.)
- 위치는 *저작*되고 *저장*된다(도출 아님). LLM은 "3열 2행에 리스트" 식으로 좌표를 직접 지정한다.

### 1-3. 닫힌 footprint

폭 `w`는 12의 약수 **닫힌 5종** — ⅙(2)·¼(3)·⅓(4)·½(6)·full(12). 높이 `h`는 **{1,2,3}**. 각 위젯 타입은 이 중 **자기 부분집합**만 선언(§2). 자유 리사이즈 없음(iOS small/med/large식 이산 선택).

### 1-4. 불변식 (검증의 진실)

1. **범위** — 모든 위젯이 12×3 격자 안: `1 ≤ x`, `x+w-1 ≤ 12`, `1 ≤ y`, `y+h-1 ≤ 3`.
2. **겹침 0** — 두 위젯의 셀 사각형이 교차하지 않는다. (유일한 배치 제약. 빈 칸은 허용 — 저작자가 채우거나 비워둠.)
3. **footprint 적법** — `(w,h)` ∈ 해당 타입의 선언된 footprint 집합.
4. **함수 금지** — `config`·`header`는 직렬화 가능해야 한다. 콜백·resolver는 코드가 `id`/`key`로 주입(FieldSpec `lookupKey` 규율과 동일).
5. **닫힌 값** — 좌표·footprint·타입은 전부 유한. 임의 px·자유 크기 없음.

> 검증기 `validateLayout(spec)` → 위 5개. 렌더러·편집기·LLM 산출물이 화면에 가기 전 관문(강제 3층의 배치판).

### 1-5. 예제 3개 (모델이 실화면을 덮는지 검증)

**빈 페이지**
```ts
{ header: { title: '새 대시보드' }, bento: { widgets: [] } }
```

**리스트 페이지** (ListWidget 하나가 전폭 — ListPage 개념 흡수)
```ts
{ header: { title: '고객 관리', primaryAction: { label: '신규 고객', ref: 'new-customer' } },
  bento: { widgets: [
    { id: 'w1', type: 'ListWidget', x: 1, y: 1, w: 12, h: 3,
      config: { columns: [...], filters: [...], dataKey: 'customers' } },
  ] } }
```

**대시보드** (KPI 4 + 리스트) — 12×3 = 36칸 정확히
```ts
bento: { widgets: [
  { id:'s1', type:'StatWidget', x:1,  y:1, w:3, h:1, config:{ label:'오늘 발주', metricKey:'todayOrders' } },
  { id:'s2', type:'StatWidget', x:4,  y:1, w:3, h:1, config:{ label:'미승인', metricKey:'pending', tone:'danger' } },
  { id:'s3', type:'StatWidget', x:7,  y:1, w:3, h:1, config:{ label:'매출', metricKey:'revenue' } },
  { id:'s4', type:'StatWidget', x:10, y:1, w:3, h:1, config:{ label:'완료', metricKey:'done' } },
  { id:'l1', type:'ListWidget', x:1,  y:2, w:12, h:2, config:{ columns:[...], dataKey:'recentOrders' } },
] }
```
→ 이 셋이 실화면을 덮으면 모델이 맞은 것. (덮지 못하는 화면이 나오면 그게 모델 수정 신호.)

## 2. Widget 층 계약 (신설 층 — 유기체와 Page 사이)

### 2-1. 정의

**Widget = Bento 격자의 칸(들)을 점유하는, 스스로 완결된 배치 단위.** 도메인 무지(데이터로만). 각 위젯이 선언하는 것:

```ts
type WidgetDef = {
  name: WidgetType;
  footprints: [number, number][];        // 닫힌 (w,h) 집합. 예: StatWidget=[[2,1],[3,1]]
  render(config, tileBox): ReactNode;     // config→본문. tileBox=배정된 픽셀 박스(fit용)
  configSchema?: ...;                      // 도메인 config의 형식(선택)
};
```

### 2-2. 소유·규율

- **raised 표면 소유** — 모든 위젯은 `surface-raised + elevation + radius + padding`으로 바닥(sunken) 위에 떠오른다(공유 base로 일관). blend 차단.
- **헤더 크롬 없음** — 페이지 정체성은 PageHeader가 소유. 위젯 타이틀은 *내용*(차트 제목)일 뿐 크롬 슬롯이 아니다. (필터·툴바 같은 *기능* 존은 위젯 내용으로 유지.)
- **고정 타일 적응** — 타일 높이는 footprint×ROW_UNIT 고정. 위젯은 넘치면 *내부에서* 처리(페이지네이션/요약) — 페이지를 밀지 않는다. 「01」 **축 예약(stability band)** 지향을 위젯 내부 전환 밴드에 적용(필터칩·벌크바 등이 행 높이 안 흔들게).
- **도메인 무지** — `config`는 스키마/데이터 key만. 위젯은 "고객"을 모른다(헌법 1).
- **관계** — 위젯은 보통 **유기체를 호스팅**한 것: `ListWidget`=DataTable/TanStack 엔진, `StatWidget`=SummaryCard, `ChartWidget`=차트. "같은 데이터, 벤토용 포장."

### 2-3. 레지스트리

위젯 타입은 닫힌 레지스트리(`_catalog` 동형). 새 위젯 = 사람 큐레이션(헌법 4). 초기 후보: `ListWidget`·`StatWidget`·`ChartWidget`·`CalendarWidget`·`HierarchyWidget`.

## 3. Bento 런타임 (LayoutSpec → DOM)

### 3-1. Page 골격

`Page` = **sunken 바닥(전면 소유)** + `~1200 캡 중앙정렬`(넷바 좌측·AppShell v0.46) + **PageHeader**(제목·탭·CTA) + **Bento**. (AppShell은 셸 크롬만, Page가 바닥·헤더·격자 소유.)

### 3-2. Bento 배치

12열 × 3행 고정 셀(ROW_UNIT ≈ 180, 1280×720 무스크롤 예산). 각 위젯을 좌표로 찍는다:
```css
.widget { grid-column: {x} / span {w}; grid-row: {y} / span {h}; }
```
- 위젯 = raised, 바닥 = sunken.
- **무스크롤** — 12×3 초과 배치 불가(편집기가 막음). 더 필요하면 헤더 탭(페이지 넘김).
- **fit-to-height** — 타일 픽셀 높이 → 들어가는 행 수(ListWidget pageSize 등). MVP는 고정, 이후 실측(ResizeObserver).
- **반응형 리플로우** — 뷰포트 아니라 `@container`(부품 자기 폭)로 열수 강등(태블릿↓·폰 1열 스택+스크롤=명시 예외). 「page-widget-grid-direction」 결정 이월.

## 4. 편집 연산 (pure ops — UI 없이 테스트 가능)

`LayoutSpec` 순수 변환. UI는 트리거만:
```ts
place(spec, {type, x, y, w, h}): LayoutSpec     // 겹침·범위 검사 통과 시 추가
move(spec, id, x, y): LayoutSpec                 // 새 위치 겹침·범위 검사
resize(spec, id, w, h): LayoutSpec               // footprint 적법·겹침 검사
remove(spec, id): LayoutSpec
validate(spec): Issue[]                          // §1-4 불변식
```
- 겹침/범위 위반은 연산이 거부(no-op + 사유). 편집기는 그 결과로 "여기 못 놓음" 피드백.
- **undo/redo = LayoutSpec 스냅샷 히스토리**(불변 모델이라 공짜).
- 편집기·LLM이 같은 ops를 쓴다 → 동기 자동.

---

## 5. 편집기 (얇은 층 — 렌더러 + 오버레이 + ops)

- **뷰 = 런타임 렌더러 재사용** + 편집 오버레이(핸들·갤러리). 편집 모드 토글.
- **갤러리 = 위젯만**(후보에 원자·유기체 날것 없음 — "Page엔 위젯만" 규칙이 편집기에서 강제).
- **배치** — 갤러리에서 위젯 선택 → 빈 칸에 놓기(겹침 방지). **크기 = 닫힌 footprint 칩**(자유 리사이즈 없음).
- **이동/삭제** — 드래그로 빈 칸에 옮기기(무 reflow — 놓은 자리 그대로), × 삭제.
- 저작 단계라 라이브 reflow·중력 불필요(단순).

## 6. 헌법 정합 (왜 이게 우리답나)

| 원리 | 적용 |
|---|---|
| 헌법 1 (도메인=데이터) | 배치·도메인 전부 `LayoutSpec`(config)로만. 위젯은 도메인 모름 |
| 닫힌 값 | 좌표·footprint·타입 유한. 자유 크기·임의 px 0 |
| 함수 금지 | config 직렬화·LLM-emittable(FieldSpec 규율) |
| 단일 진실 | `LayoutSpec` 하나 — 편집기·LLM·런타임 공유 |
| 축 예약 지향 | 위젯 내부 전환 밴드가 타일 높이 불변 유지(무스크롤 pageSize 안정) |
| 무테 지향 | 바닥 sunken·위젯 raised = 톤·음영으로 분리(윤곽 아님) |

## 7. 하드 결정 (설계에서 못 박음)

| 문제 | 결정 |
|---|---|
| 좌표 모델 | **명시 `x,y,w,h` · 무 reflow** (저작=별도 단계라 중력 불요) |
| 배치 제약 | **겹침 금지 + 범위**만. 빈 칸 허용(강제 채움 없음) |
| footprint | 위젯별 **닫힌 (w,h) 집합** (w=12약수, h=1~3) |
| fit-to-height | 실측 목표, **MVP는 고정 pageSize** |
| 반응형 주인 | **`@container`**(부품 자기 폭) — 셸 tier 아님 |
| persistence | **소비처/백엔드** (패키지는 모델·렌더러·편집기만) |
| undo/redo | **스냅샷 히스토리** (불변 모델) |

## 8. 구현 순서

```
① LayoutSpec 타입 + validate + 예제 3개 (모델 확정)
② pure ops 모듈 (place/move/resize/remove) + 테스트
③ Bento 런타임 렌더러 (spec→DOM) — view/edit 공유
④ Page 골격 + PageHeader
⑤ 편집기 (렌더러 + 오버레이 + ops + 갤러리)
⑥ 실화면 증명 (customers 리스트페이지 · 대시보드)
```
UI(편집기)는 **맨 마지막.** 모델·ops·렌더러가 먼저 서야 편집기가 그 위 얇은 층이 된다.

---

## 미해결 (설계 중 결정 대기)

- ROW_UNIT 실측 확정(≈180 잠정) · 콘텐츠 캡 폭(넷바 260 고려 시 ~1000~1200) · fit-to-height 실측 전환 시점.
- 위젯 raised 표면 = 공유 base 컴포넌트 vs 각 위젯 개별 — DRY 판단(구현 시).
- `ListWidget`이 이미 자기 raised 표면 소유(현행) → Widget 공유 base로 통일 여부.
