# 03. 로드맵과 미해결 (어디로 가는가)

> 본 문서는 ERP No-Code 빌더 프로젝트의 **참조 문서**이다. 상위 원칙·규칙·색인은 「프로젝트 지침」을 따른다.
> 본 문서는 작업 순서·진행 상황, "올바른 방식" 문제, 미해결 지점을 다룬다. 가장 빈번히 갱신된다.

---

## 작업 순서 (로드맵)

1. ✅ 토큰 세트 확정 (theme.ts, mantine.d.ts)
2. ✅ **검증** — `npx tsc --noEmit` EXIT=0. 인터페이스 이름(`MantineThemeColorsOverride`/`MantineThemeOther`/`MantineThemeSizesOverride`) 전부 정상 확인.
3. ✅ **첫 부품 + 강제 인프라** — Button 래퍼(그물 1) + eslint 두 문(그물 2) 구현·probe 검증 완료. 별도 DSL 라이브러리 레포로 분리(특정 ERP 레포 아님).
4. ✅ **원자 분류·기준 확정** — 의미/레이아웃 원자 + 배치 프리미티브 구분, 1차 원자 집합 목록(「02. 토큰과 구현」), 판별 기준·경계 닫기 규칙·크기(밀도)·공간 장부(「01. 규칙과 구조」).
5. ✅ 의미 원자·레이아웃·프리미티브 prop 규격 확정 — 의미 원자 22 + 레이아웃 3 + 프리미티브 3, 개별 표까지(→ 「02」 원자 prop 규격 절). 입력군 3골격 + 표시·텍스트 3묶음 + 횡단 규칙 4개로 수렴(error를 입력 원자에서 제거하며 "error는 쪼갠다" 규칙이 사라져 5→4). **→ 22 원자 전부 래퍼 구현·검증 완료(tsc·eslint·강제 발화). 색·타이포·테두리는 "역할 변수 통로"(CSS 변수)로 통일(→ 「02」 역할 변수 통로 절).** (Stage5에서 Popover·Image 추가 → 의미 원자 **24**. 22는 Stage4 시점 수치.)
6. ✅ 첫 분자 — FormField 확정 — 방식 A(컨트롤을 children으로). 장식(label·withAsterisk) + 에러 표현(메시지 + 테두리)을 독점. 입력칸은 에러를 모르고, 테두리는 CSS 역할 변수(--field-border)로 FormField가 덮음(→ 「02」 분자 prop 규격). "분자가 상태를 고정한다"의 첫 사례. (description은 placeholder와 경쟁 경로라 미채택 — 「02」.) **구현·검증 완료.**
6-A. ✅ **일반 분자 확보 (kk 무관, 압도적 우선)** — 02가 적어둔 분자 후보부터: MultiSelect(Select+Chip), 로딩버튼(Button+Spinner), FileUploader, DateRangeField 등. 분자까지는 어떤 ERP에도 있는 보편 부품이므로 빈도 조사 없이 만든다. **판별 기준: "이 부품 정의에서 kk를 빼도 말이 되는가?" — 안 되면 그건 부품이 아니라 스키마다.** 
(진행: FormField·MultiSelect·DateRangeField·InputGroup·FileUploader·Pagination·IconButton·Callout ✅ — 보편 분자 **8** 구현·검증 완료. 조합 커버리지(모든 입력 원자를 FormField·InputGroup 슬롯에 꽂아 tsc 통과)도 확인. SegmentedControl·TabBar 원자 추가(의미 원자 **22** — prop 표 실측. 과거 21/23 표기는 off-by-one 오기). FileButton은 폐기(파일 업로드는 4단계 상태가 본질 → FileUploader 단일 경로). 분자 중 MultiSelect·Pagination·FileUploader는 "원자 + 격리된 Mantine 엔진(Combobox/Pagination/Progress)"으로 조립 — 도메인 무관·격리 유지, 순수 원자 조합만은 아님. **IconButton**은 Button을 아이콘 전용으로 고정한 named 분자(renderAction이 iconOnly 라우팅), **Callout**은 인라인 비휘발 안내(토스트와 의미 분리).)

6-B. ⏳ **kk 화면 빈도 지도 (병렬 가능, 유기체 착수 전 선행)** — 클로드 코드로 kk 로컬을 스캔해 "xx형 페이지 N개 / yy형 모달 N개" 식의 *현황* 지도를 받는다. 이는 *무엇이 부품인지*를 kk가 정하는 게 아니라(헌법 1번 — 도메인은 컴포넌트로 안 샘), *무엇부터 부품화할지 우선순위*를 실측으로 정하는 것이다. N≥3이 지금 추출할 후보(rule of three), N=1은 보류. 현황→부품 추출은 사람의 일(11-1).

6-C. ✅ **유기체 디벨롭 (빈도순)** — Modal·DataTable·EmptyState·PageHeader·DescriptionList·AppShell 6개 **구현·검증 완료**(「02」). 공유 패턴 2개(셀/값 type enum `text|badge|number|currency|date|actions`, actions 배열)를 공유 모듈로 선추출. AppShell은 A안(상단바 없음·로고 넷바 편입). DetailPage 통째는 템플릿(7번)으로 미룸.

6-D. ✅ **ERP 공통 셸** — 좌측 넷바(고정) + **우상단 바(고정)** + 콘텐츠. (초기 A안=상단바 없음에서 **B안=상단바 도입**으로 진화.) 프로필 카드는 넷바 하단→상단바 우측으로 이동, 알림 bell(안 읽음 점) 신설, 우측 밀착 `[알림][프로필]`. 좌측은 비움(넷바가 전체 경로를 제공해 브레드크럼 중복), 로고는 넷바 최상단(a형). 넷바 우측·상단바 하단 그림자로 둘 다 떠 있는 고정 패널. 모바일 햄버거는 상단바 좌측. kk 전용이 아니라 모든 ERP 공통(교집합).
7. ✅ **스키마 층 1차 + 1차 확장** — `FieldSpec`(name·label·type·required·placeholder·options·lookupKey·span·**pattern·mask·requiredWhen·disabledWhen**) + `FieldType` 7종(text·number·textarea·select·date·checkbox·**lookup**) + `buildZodSchema`(Zod: 타입+required+**정규식 refine+조건부 필수 superRefine**, 패턴 가드). 마스크 카탈로그(`_masks.ts`, phone). 도메인은 오직 FieldSpec[]로만 진입(헌법 1번). 함수(resolver)는 스키마 밖(코드 주입, patch 시그니처). **남은 것: min/max·교차필드(끝≥시작)·다중 술어·위저드 스키마는 데이터 계약 수령 후.**
8. ⏳ **조립 계약 + 카탈로그 문서화** — 헌법(「01. 규칙과 구조」)을 LLM 컨텍스트로 + 부품 어휘를 LLM이 읽을 지도로(「강제 vs 인지」).
9. ✅ **첫 수직 슬라이스 1종** — 고객 관리(목록 ListPage + 상세 DetailPage + 신규등록 Modal/FormSection)를 **config-driven으로 증명**(→ 「02」 템플릿/조직 절, `src/app/customers/`). 도메인 0줄 — schema(FieldSpec[])·rows·resolver만으로 작동. **남은 것: 위저드(MultiStepFormWizard)는 N단계 = 1엔진 + N스키마로 별도 증명 예정(현재는 단일 폼/목록/상세 슬라이스).**

### 실용 경고 (과도한 선제 추상화 주의)
- 모든 화면을 알기 전에 완벽히 일반적인 위젯 프레임워크를 먼저 짜면 틀린 프레임워크가 나온다.
- 같은 패턴이 **세 번째 반복될 때** 어휘로 추출한다(rule of three). 어휘가 실사용에서 *발생*하게 둔다.
- (ERP는 도메인이 닫혀 있어 이 위험이 비교적 작지만, 요구사항은 만들면서 발견된다.)
- **도메인 누수 주의 (헌법 1번의 실무 형태):** 부품은 kk를 모른다. kk(작업 중인 실제 ERP)는 이 시스템의 *부분집합*이어야 하며, kk 전용이라 다른 ERP엔 안 맞는 부품(여집합)이 생기면 안 된다. kk가 필요해서 만들고 싶어지는 부품은 부품이 아니라 *스키마*다(예: "발주항목카드"가 아니라 DataTable + 발주 스키마). 판별: 정의에서 kk를 빼도 말이 되는가.

## "올바른 방식" 문제 (가장 어려운 핵심)

자연어 설명을 받아 유한한 부품으로 위젯을 "올바르게" 조립/배치하는 판단. **이건 하나가 아니라 네 겹이고, 정의 가능한 것과 불가능한 것이 섞여 있다. 분리가 핵심.**

1. **하드 제약** — 구조적으로 허용되는 것(타입·스키마·린트가 강제). 정의 가능, 유한.
2. **기본값** — 명세가 비었을 때 적용되는 것. 사용자가 저작. 정의 가능.
3. **소프트 관습** — 권장 관용(예: "발주서엔 주소가 먼저"). 문서화하되 강제는 안 함.
4. **순수 판단** — "이 사업체엔 어떤 위젯이 맞는가". **정의 불가능. 자동화 대상 아님.**

> **촘촘하게 짜야 하는 건 1~3(정의 가능 층)이다. 4번까지 정의하려는 게 함정.**
> 4번은 정의하지 말고 사람에게 라우팅한다.

**빈칸은 LLM이 추측으로 메우게 두지 않는다.** 명세가 빈 선택 슬롯은 → 기본값을 적용하거나, 빈칸을 *드러내서 사람에게 되묻는다*. 시스템의 일은 "맞게 추측"이 아니라 "빈칸을 드러내기".

### 11-1. 규모의 역설 (현재 전략에 직결)

- **큰 규모:** 클라이언트가 *카탈로그에 맞춘다* → LLM의 판단 부담↓.
- **작은 규모(현재):** 사용자가 클라이언트와 소통하며 *사전 구조 설계 후* LLM 투입 → LLM의 판단 부담↓.
- 양 극단 모두 LLM 부담이 준다. **함의: 지금은 "올바른 방식"의 판단 엔진이 LLM이 아니라 사람(나)이다.**
- → 지금 단계엔 판단 자동화 기계를 미리 짜지 말 것. 시스템엔 *실행 충실도*만 요구한다. 정의 가능한 층(제약·기본값·관습)만 촘촘히.

### 11-2. 판단은 "정의"하지 말고 "축적"한다

순수 판단(4번)을 함수로 만들려 하지 말 것. 대신:
- 지금: 클라이언트별 "이 페이지엔 이 위젯들" 결정을 사람이 내린다.
- 축적: 그 결정들이 **이름 붙은 선례 템플릿**으로 쌓인다("가구 업체 발주 페이지는 이렇게").
- 나중(규모↑): LLM은 판단을 *계산*하는 게 아니라 *쌓인 선례 중에서 고른다*.
- → 판단은 끝내 함수가 되지 않고 **점점 커지는 예시 라이브러리**가 된다. (rule of three의 페이지 단위 적용)

### 11-3. 위젯 변형: 옵션을 쌓지 말고 위젯을 늘려라

"어떤 사업은 최고/최저, 어떤 사업은 입력칸" 같은 변동성을 한 위젯의 옵션 토글로 다 받으면, 토글 15개 = 2^15 구성 = 무한 공간의 부활(새 옷 입은). **촘촘함(정의 밀도) ≠ 유연함(옵션 개수).**
- 차라리 의견이 뚜렷한 별개 변형 몇 개로: 날씨위젯A(기본) / 날씨위젯B(최고최저 포함) / 입력형은 아예 다른 위젯.
- Button의 prop 30개 함정과 같은 원리. "유한집합" 본능이 방어선.

### 11-4. 아직 안 푼 지점

- **스키마 층 형식화 (1차 해결, 확장 진행 중).** 강점/약점 정확히: *무엇이 부품화돼야 하는지 판별하는 도메인 감각*은 강점(ERP 만들어본 자산). *그걸 형식 규칙(DSL 문법)으로 정리하는 형식화*가 약점. → 사용자가 "무엇이 부품이어야 하고 무엇이 자유여선 안 되는가"를 판단하고, Claude가 이를 스키마 문법으로 형식화한다. **1차 FieldSpec 골격 확정(→ 「02」 스키마 층). 남은 것: 정밀 검증·교차필드·조건부 필드.**
- 위저드 스키마 구조: 단계 → 섹션 → 필드 배열, 필드 타입·필수·검증규칙, 완료 추적, 임시저장, "다음" 검증 게이팅, 조건부 필드. **(현재 단일 폼/목록/상세 슬라이스까지. 위저드는 다음.)**
- ~~**검증기(Zod)**~~ → **(해결, 확장)** `buildZodSchema(FieldSpec[])` — 타입 7종+required에 더해 **정규식(`pattern`, 가드)·조건부 필수(`requiredWhen`/`disabledWhen` superRefine)**까지. 마스크(`mask`)는 입력 변환(렌더 측), pattern은 검증(스키마 측) — 별개 축. 남은 것: min/max·교차필드(끝≥시작)·다중 술어(→ 「02」 스키마 층).
- **카탈로그 진화/버전 관리** — 새 부품 추가 시 기존과의 일관성을 사람이 어떻게 보장하는가(헌법이 사람에게도 강제되는가).

소프트 관습 후보(카탈로그 문서용, 8번) — 단일선택 부품 경계: 데이터 선택(폼 제출값)은 Radio/Select, 같은 대상 뷰·모드 토글(즉시 전환, 비제출)은 SegmentedControl, 다른 구획 전환(패널 교체)은 TabBar/Tabs. 셋의 결과물이 다르므로 경쟁 경로 아님 — 단 kk처럼 단일선택에 Segmented를 남용한 사례는 의미 경계로 차단. 강제 아님(의미 판단에 사람 여지). "올바른 방식" 3번(소프트 관습) 두 번째 등록.

한 화면 primary 행동은 하나. 헤더(PageHeader)에 주 행동이 있으면 EmptyState의 action은 비운다(우리 기본 — 헤더 안정성). first-use 온보딩처럼 헤더 액션이 없으면 EmptyState action 살림. 강제 불가(부품끼리 서로 모름) 

Autocomplete — 보류 유지, 확인 대상: 측량 3건("분류 입력")이 "기존 분류 중 검색 선택"(Combobox/searchable 회귀)인지 "자유 텍스트 입력"(진짜 Autocomplete)인지 그 3건 코드 확인 후 판단.

### 11-5. 이번 세션 해결/산출

### 11-13. v0.10.0 산출 (애플식 squircle 곡률 + radius 상향)

> ERP 모서리에 애플식 통일성(squircle)을 도입. radius 스케일(sm/md/full)은 유지하되 값을 키우고, 그 위에 연속 곡률을 단일 토큰으로 얹었다. tsc·eslint EXIT=0, 크롬 화면 검증(아바타·스피너 원형 유지 + 카드 squircle 확인). 커밋·푸시·버전 태그(v0.10.0) 완료, **publish는 보류**(소비자 영향 0).

- **corner-shape(superellipse(2)=애플 squircle)을 단일 토큰으로 추가.** `theme.ts`의 `cornerShape` → `cssVariablesResolver`가 `--corner-shape` 방출(역할 변수 통로 — 색·타이포·아이콘 정렬과 동일 구조). 컴포넌트엔 prop으로 안 연다(헌법 5 — 0~100 smoothing 스칼라 노출 금지, 전역 토큰 1개).
- **박스 전용 opt-in(`squircle.css` 화이트리스트).** Button·Paper·Input·Modal·Popover·SegmentedControl에만 `corner-shape` 적용. **방향 결정:** 전역(*) 후 원형 제외(blacklist)는 빠뜨린 원형(Radio 등)이 각지므로 "박스에만 켠다(whitelist)"로 뒤집음 — 목록 밖(Avatar·Spinner·Switch·Chip·Radio·알림 점)은 자동 round. **squircle은 원/알약의 둥근 곡선까지 각지게 만들기 때문**(원→둥근 사각형). border·box-shadow·outline이 모양을 네이티브로 따라가 clip-path식 테두리·그림자 충돌 없음(MDN 확인).
- **radius 값 상향(스케일·키는 불변): sm 4→8, md 8→16.** squircle 곡률은 반경이 작으면 드러나지 않아(8px엔 곡률 바꿀 모서리가 8px뿐) md를 키워야 카드에서 보인다.
- **SummaryCard 아이콘 칩 sm 고정.** md=16이 작은 아이콘 칩(~36px)을 거의 원형으로 만들어 sm(8px)으로 복원(이전 md=8px 동치).
- **브라우저 정책:** corner-shape는 Chromium만(2026.06 ~67%, Safari/FF 미지원), **graceful fallback** — 미지원 시 평범한 둥근 모서리. radius 값은 전 브라우저 동일하므로 구조적 통일성 유지, squircle은 점진 향상 층. (사파리 혼재 환경이라 경로 A=네이티브 corner-shape 채택; 경로 B=clip-path는 테두리·그림자·no-px 충돌로 비채택.)
- **점검에서 짚은 것(동업자 판단):** ① raw-div 보조 표면(Callout·FileUploader 드롭존·DataTable 헤더)은 화이트리스트 밖이라 radius bump은 받고 squircle은 안 받음 — 경미한 cosmetic 갭, 수용. ② `Menu.tsx`의 `borderRadius: 4` 하드코딩 리터럴(토큰 아님)은 기존 드리프트, 차기 정리. ③ 소비자는 버전 bump+재설치 시 자동 반영(SSOT) — API/타입 무손상, 단 전 화면 시각 변화(둥글어짐)라 의도된 버전 업(minor)으로 표기.

## 흡수 전략 (전략 원칙 — 명문화)

> **우리는 "ERP를 닫힌 부품으로 조립한다"는 *방식*을 만들지만, 그 방식을 떠받치는 엔진·렌더링·인프라까지 전부 직접 만들지 않는다. 검증된 외부를 *흡수*한다.**

- **이미 굴지의 기업들이 같은 "방식"으로 접근했다** — JSON/스키마로 UI를 구동하는 스키마-드리븐 렌더링(예: Vercel **json-render** 류), 닫힌 컴포넌트 레지스트리, 디자인 토큰 시스템. 이건 우리만의 발명이 아니라 *업계가 수렴 중인 패턴*이다.
- **그래서 "내가 전부 만든다"는 욕심을 버린다.** 엔진(스키마→렌더 변환·resolver·런타임)은 검증된 외부로 **흡수**하고, 우리는 *대체 불가한 고유 가치*에만 집중한다:
  - **디자인 토큰 + 닫힌 부품 카탈로그**(이 DSL의 헌법·강제 3층) — 통일성의 원천.
  - **`FieldSpec`/스키마 층**(도메인 진입로) — ERP 도메인 형식화.
  - **ERP 특화 부품**(HierarchyExplorer·ObjectCard·정산/발주 조립 패턴) — 도메인 자산.
- **판별 기준:** "이게 우리 ERP-DSL의 고유 가치인가, 아니면 누구나 쓰는 범용 엔진인가?" 후자면 흡수(외부 채택), 전자면 직접. (헌법 4의 "큐레이션"이 *부품* 차원이라면, 흡수 전략은 *인프라* 차원의 같은 사상 — 우리가 통제할 경계와 빌려올 경계를 가른다.)
- **현 단계:** kk 건은 지금 구조(자체 렌더)로 마무리하고, 그 이후 json-render 류로 엔진을 흡수하는 전환을 디벨롭한다. 토큰·FieldSpec·ERP 부품은 흡수 후에도 우리 것으로 남는다(엔진만 교체, 어휘·문법·도메인은 유지).

### 11-21. v0.53.0 산출 (MobileCalendar 3축 범례 + 오늘/선택 위계 교정)

**칩 줄 3축.** 분류(anchor) / 표식(mark) / 태그(annotations) — 셋은 이벤트에 *동시에* 붙는 축이라 1차원 분류가 아니다. 한 줄에 두되 축 사이는 divider가 가른다(축 사이 AND, 축 안 OR — 그 논리 경계의 표시). `hidden` 접두로 축을 구분: `k:`(분류) `m:`(표식) `t:`(태그). 이벤트 필터에 mark 조건 추가.

**색은 메인 축만.** `anchor` 색은 곧 **바의 색**이라 칩이 그 톤이면 대응을 배울 필요가 없다. 반면 `mark`(작은 표식)·태그(배너·틴트)까지 칠하면 칩 줄이 무지개가 되고 *어느 색이 바 색인지도 흐려진다* → 나머지 두 축은 **중립 필터 칩**, 구분은 divider와 라벨이 맡는다. (`mark.values[k].color`는 바 안 표식에만 쓰인다.)

**오늘 = 꽉 찬 원 / 선택 = 윤곽 원 (교환).** 전엔 반대라 오늘이 윤곽뿐이라 눈에 안 띄었다. iOS와 같은 위계로 정정: **오늘은 항상 거기 있는 기준점**이라 가장 강한 표현을 갖고, **선택은 탭하면 다른 화면으로 넘어가는 일시적 표시**라 약하게 둔다. 겹치면 오늘이 이긴다(이미 최대 강조라 더할 게 없다).

**데모.** `SITE_ENCODING`에 `mark` 축(담당) 추가 — 3축 칩과 v0.51.0에서 만든 **바 안 표식 슬롯**이 그제야 화면에서 증명된다.

### 11-22. v0.53.1 산출 (MobileShell 탭 활성 표시 — 틴트 알약)

**증상.** 하단 탭이 "지금 어느 탭인지"를 말하지 않았다. 배선(`activePath`)은 멀쩡했고, 표현이 `--text-primary` vs `--text-secondary`(검정 vs 회색) **명도차 하나**뿐이라 16px 글리프에서 안 읽힌 것. `_catalog`는 토큰을 `primary(탭 활성)`이라 적어놨는데 코드의 `color="primary"`는 브랜드 navy가 아니라 *텍스트 위계*의 primary였다 — 같은 이름이 두 어휘에서 다른 뜻이라 의도가 조용히 누락됐다.

**진짜 원인은 색이 아니라 채워짐.** 잘 만든 앱들의 주력 채널은 hue가 아니다: iOS는 filled 심볼, 카톡·인스타는 활·비활성이 **같은 색**이고 fill 대비만으로 상태를 말한다. 우리 아이콘 세트는 outline 전용이라 그 채널이 통째로 닫혀 있고, 그래서 명도차 하나만 남았던 것. M3의 active indicator 알약이 outline 세트로 fill의 무게를 내는 정공법이라 그걸 택했다. (11-21의 "오늘 = 꽉 찬 원"과 같은 이야기 — 강조는 색보다 채움이 싸게 읽힌다.)

**태블릿 레일과 같은 어휘.** 활성 = 틴트 배경 + 아이콘색 + 라벨색. `.erp-rail-item[data-active]`이 이미 내린 판단을 모바일에 반복할 뿐이라 **새 시맨틱 역할·새 토큰 0**, `Icon`/`Text`의 prop도 그대로. (설계 중 `text.brand` 역할 신설을 검토했다가 폐기 — 선례가 이미 있는데 토큰 층을 새로 파는 건 과했다.)

**색은 `--mantine-color-primary-light`.** 태블릿의 불투명 `primary-0`을 복사하지 않은 이유: 다크에서 활성 타일이 밝은 면이 되고 그 위에 흰 아이콘이 얹힌다. `-light`는 같은 navy 사다리에서 Mantine이 *모드별로* 내주는 반투명 틴트(라이트 .1 / 다크 .15)라 양쪽에서 성립한다. **태블릿 레일의 같은 결함은 미해결로 남긴다**(범위 밖 — 고치면 두 셸이 값까지 일치).

**기하는 의사요소로.** `.ms-tab-ico`에 padding을 주면 그 안에 `left:100%`로 절대배치된 카운트 배지가 활성일 때만 밖으로 밀려 자리가 튄다. `::before`는 기하를 안 건드려 활·비활성 레이아웃이 동일하다. `z-index:-1`이 셸 배경 뒤로 새지 않게 `.ms-tab`에 `isolation`으로 스태킹 문맥을 가둔다. 알약 42×22 = M3의 24dp:64×32dp 비율을 16px 아이콘에 축소. 아이콘–라벨 간격 `xxs`→`xs`: 알약이 위아래로 3px 삐져나오므로 거리는 아이콘이 아니라 **알약 가장자리**에서 잰다(M3도 인디케이터 기준).

**상단 인디케이터 막대는 여전히 없다.** 알약은 선이 아니라 톤이라 헤어라인 체계와 안 다툰다.

**미해결(이번에 확인).** 탭 라벨 11px 규칙(`mobileshell.css`)이 **죽어 있다** — `Text`가 `font-size`를 인라인 style로 박아 어떤 선택자도 못 이겨서, 라벨은 의도한 11px가 아니라 모바일 caption 13px로 렌더된다. 고치려면 `.ms-tabs { --typo-caption-size: … }`로 *역할 변수*를 국소 재정의해야 한다(인라인이 그 변수를 참조하므로 안 싸운다). 색에 같은 수법을 쓰면 안 되는 이유는 크기는 "같은 역할·다른 값"이지만 색은 역할 자체가 다르기 때문.

**단일 계약 파일 = `optionset.ts`.** 저작 면이 *쓰고* 선택 면이 *읽는* 타입을 한 파일에 두고 두 면이 그것 하나를 import한다 — **변환 계층 금지의 물리적 강제**(Editor가 만든 그대로 Picker가 읽는다). `meta` 자루·탈출구 없음. `Choice`에 저작 필드 5종(`refId`·`override`·`ratio`·`formula`·`adjust`)을 *선택적으로* 얹은 것이 유일한 확장인데, 근거는 "모든 쓰기는 `onChange` 하나"라는 명세 원칙과 "값 행이 편집한 규칙이 저장될 자리가 타입에 없다"는 내부 불일치였다(§2 회신).

**템플릿이 아니라 위젯으로 해체.** 명세는 `CompositionBuilder` **템플릿** 하나였지만, 페이지 전체를 템플릿이 소유하면 소비처가 배너·헤더·높이 배관을 못 끼운다. → **위젯 2개(Picker·Outline) + 페이지 조립**으로 갈랐다. 상태가 전부 controlled라 배선 유실 0 — 명세의 콜백이 두 위젯에 나뉘었을 뿐이다. **이때 "신설 부품은 page 위 widget만, 템플릿 층 동결" 방침이 섰다**(「02」 템플릿 절). 대신 높이 배관이 소비처 몫이 되므로 `Bento`에 **`fill`(작업면 모드 — 행이 부모 잔여고를 `minmax(0,1fr)` 등분)** 을 신설해 템플릿이 갖던 viewport-fit 기하를 승계했다.

**Editor·Composer는 같은 2-pane 골격을 공유한다.** 좌=구조 트리 / 우=작업면. 두 면이 미묘하게 다르면 저작자가 매번 다시 배우므로 공유 규격을 **내부 모듈(`optionset-shared`)이 강제**한다. Editor=옵션 *정의*(트리 1층=옵션·2층=묶음, 우측=표), Composer=*부착*(트리=구성 노드, 우측=부착·순서 + Picker 통째 미리보기). **정의 수정은 Composer에서 불가** — 행 클릭·편집↗은 `onEditOption`으로 소비처 라우팅(편집기를 두 곳에 내장하면 두 벌이 갈린다). 모델 근거는 Square 동형: **옵션 정의=라이브러리 참조, 부착과 순서=노드의 속성.**

**표현은 데이터가 아니다 — 자동 도출 + 닫힌 override.** 선택 면의 생김새(cards/grid/list/chips/stepper/input)는 `selection`과 **값 개수**로 부품이 도출한다. 치수류가 자동으로 `input`(타이핑)이 되는 것도 여기서 온다 — 2700㎜를 스테퍼로 밀 수 없다. `display?`는 소비처가 예외적으로 덮는 자리고 **`OptionGroup` 타입은 불변**이다(표현을 데이터에 실으면 저작 데이터가 화면 사정을 알게 된다).

2. **`selectionMark: 'fill'|'radio'`** 신설 — 요청은 "견적안 행도 같은 부품"이었는데 목업의 견적안 행은 **선택 표현이 달랐다**(라디오+윤곽 vs pill+굵기). 한 부품이 두 표현을 가지면 "선택 표현은 prop으로 못 바꾼다"는 규율이 첫날에 깨진다. 옵션 스태킹이 아니라 *두 의미*를 가른 것(내비게이션 vs 선택)이고, 우리 `Radio`가 그룹형이라 단일 점을 소비처가 못 만든다는 사정도 여기서 해소된다.
3. **잠금 CTA** — 목업은 `disabled`+`title` 툴팁이었으나 **disabled 버튼은 포커스를 못 받아 사유가 키보드·스크린리더에 도달하지 않는다.** OptionSetPicker의 잠금 규율을 재적용: 눌리되 안 넘어가고 `disabledReason`을 액션 바 안내 자리에 danger로. 그 자리는 상시 예약이라 기하가 안 흔들린다(축 예약).
4. **값은 토큰으로 스냅** — 13.5px→body(14) · 11.5px→caption(12) · weight 750→700 · radius 10→md · padding 6/`10 14`→토큰. 기하 규칙(mark 폭 46·행 44·인셋 자동계산)은 요청대로 부품이 소유하되 **수치는 우리 눈금**이다. 그대로 박으면 토큰 단일 출처(린트가 실제로 튕긴다)와 **폰트 스케일 접근성**(rem 줌에 px가 안 따라온다 — CountBadge 선례)이 깨진다. 픽셀 동일이 아니라 규율 동일.

**목업에서 뺀 것 2:**
- **보조 버튼 아웃라인 ghost → 우리 secondary(tonal fill·무테)**: 버튼 셋이 나란한 바에서 윤곽 셋은 특히 시끄럽다(무테 지향).
- **액션 바 상향 그림자 삭제**: 대응 토큰이 없어 raw 값이 되고, 우리 하단 바 선례(OptionSetPicker 풋터·CompositionOutline 합계)가 전부 border-top 하나뿐이라 여기만 그림자를 달면 같은 자리의 바가 화면마다 달라 보인다. 불투명 배경+구분선으로 "본문이 바 밑으로 흐른다"는 신호는 이미 선다.
- **4열 격자 액션 바는 애초에 안 만들었다**(kk가 v4에서 이미 폐기) — 오른쪽 정렬만으로 자리 고정은 달성되고, 격자는 보조가 하나뿐인 탭에서 두 버튼을 양 끝으로 벌려 한 쌍으로 안 읽히게 만든다.

**첫 시각 검증에서 잡은 3건 (같은 릴리스 내 수정):**
1. **hover가 인접 구분선을 안 지웠다.** 선택은 자기 위·아래 선을 지우는데 hover는 안 지워서, 채움은 라운드 pill인데 선은 인셋(mark 아래는 선이 없다)이라 **배지 아래에서 박스 모양이 어긋나 보였다.** hover도 선을 지우게 통일 — "선택과 모양은 같고 색만 약하다"는 원칙이 구분선까지 걸린다는 걸 놓쳤던 것.
2. **선택된 행에 hover하면 회색으로 덮였다.** `button.ql-row:hover`의 특이도가 `.ql-row[data-selected]`보다 높아 실제로 이겼다 — 마우스를 얹는 순간 상태가 *약해져* 보이는 회귀. 선택 유지로 수정(Finder·VS Code·Linear 공통).
3. **라디오 점을 손으로 그렸다(가장 큰 것).** "우리 `Radio`는 그룹형이라 단일 점을 못 만든다"는 판단은 절반만 맞았다 — 원자를 그대로 못 쓰는 건 맞지만(그 원자는 그룹 *레이아웃*까지 소유하고, 여기 한 '옵션'은 행 전체다), 그렇다고 손으로 그릴 일이 아니라 **격리 구역에서 같은 베이스 프리미티브를 쓰면 됐다**(헌법 7). 손으로 그리면 지름·테두리·포커스 링·다크모드가 화면마다 갈린다. → 행을 `<label>`로 바꾸고 진짜 `<input type=radio>`(color=primary)를 담아 **화살표 키 이동·"N 중 M 선택됨" 낭독**까지 네이티브로 회수. (input은 interactive content라 `<button>` 안에 못 들어간다 — 구조가 갈리는 지점이었다.)
   → **규율로 승격**(01 §4-D 보강): raw 컨트롤을 짜기 전에 "아톰이 못 맞추나"뿐 아니라 **"아톰이 쓰는 프리미티브를 직접 쓸 수는 없나"**를 먼저 묻는다.

**경계 정정 — 두 층을 섞지 않는다(감사 기준).** 처음 감사는 *raw 값·기하*(임의 비율·매직넘버·인라인 px)와 *부품 재작성*을 한 목록에 섞어 놨는데, 오너 판단은 **전자는 허용**이다: 기존 부품으로 안 되는데 시각적 완성도가 필요하면 raw 값을 써도 되고, rule of three를 그렇게까지 좁게 적용할 일도 아니다. **금지선은 하나다 — 이미 있는 컨트롤을 손으로 다시 만들거나, 부품 안쪽을 바깥에서 다시 칠하는 것.** 컨트롤은 픽셀이 아니라 *동작·상태·키보드·접근성*을 나르므로 손으로 그리면 그게 전부 사라지고, 부품을 밖에서 덮으면 부품은 자기가 A인 줄 아는데 화면은 B라 계약이 조용히 깨진다.

그 기준으로 실제 위반은 **2건**이었다:
1. **라디오를 손으로 그렸다**(위 3번) — 점만 CSS로 만들고 화살표 이동·"N 중 M 선택됨" 낭독·포커스 링을 통째로 잃었다.
2. **`.dp-locked > button`으로 Button을 바깥에서 다시 칠했다** — 잠금 CTA를 회색으로 덮었는데, 부품은 자기가 primary인 줄 알고 있고 Button 내부가 바뀌면 같이 깨진다. → **Button의 어휘로 표현**한다: 잠금 = `variant="secondary"`(지금은 주 행동이 아님). CSS 오버라이드 0.

아래 4건은 같은 감사에서 함께 손봤지만 *위반이 아니라 정리*다(임의 비율 → Grid는 「01」 조항이라 그대로 유효):

**부품 미사용 감사 (같은 릴리스 내 수정 4건).** "발행 레포 위에서 목업만 보고 raw를 박았다"는 지적으로 신규 4파일을 전수 점검했다.
1. **ListDetail이 임의 비율을 raw grid로 박았다** — `.82fr 1.18fr`. 「01」이 *"비율 분할은 반드시 Grid로(임의 폭은 금지된 값이고, 비율은 구조에서 도출한다)"* 라고 못박은 바로 그 위반이다. 12열 5:7 = 41.7:58.3으로 목업과 0.7%p 차이 — **눈에 안 보이는 값 때문에 닫힌 격자를 버린 셈**이었다. `Grid`+`Grid.Col`로 교체. 덤으로 버그 하나가 드러났다: `align-items:start`를 줘서 칸 높이=내용 높이가 됐고 **sticky가 조용히 무력화**돼 있었다(붙을 구간이 0). Grid.Col의 stretch가 그 구간을 만든다.
2. **구분선을 CSS border/inset shadow로 흉내 냈다**(DecisionPanel 섹션·헤더, NoteThread 항목) — 선은 `Divider` 원자가 이미 가진 물건이다. 교체. **단 액션 바 상단 선만 CSS로 남긴다**: sticky로 떠 있는 요소가 자기 선을 지녀야 하고, 흐름에 놓인 Divider는 스크롤과 함께 흘러가 버린다.
3. **토큰 밖 매직넘버 2건** — 부제 `margin-top:3px`·메타 `margin-top:2px`. 둘 다 "한 덩어리로 붙인다"는 뜻이라 `Stack gap="xxs"`가 정답이었다.
4. **스켈레톤 폭을 TSX에 인라인 px로 박았다** — 소비처에 하지 말라고 막아둔 바로 그 형태. CSS 클래스(+`nth-child` 폭 변주)로 이전.

**raw로 남긴 것과 사유(01 §4-D 태그):** `mark` 배지=**전용 소유**(Badge는 light 틴트뿐이라 무게 사다리를 못 내고, 고정폭 46은 Badge가 아니라 *이 목록의 정렬* 사정이다 — 무게 사다리가 재발하면 Badge variant로 승격) · 제목·메타 텍스트=**승격 후보**(아래) · `flex:1;min-width:0` 래퍼=프리미티브 미노출 값(다수 선례).

**발견: `Text`에 truncate 구멍이 없다 — rule of three를 한참 넘겼다.** 말줄임을 손으로 짠 CSS 파일이 **8개**(assignpicker·board·calendarpage·collector·mobilelist·mobileshell·optionset·queuelist). 매번 "Text 원자가 truncate를 미노출해서" 라고 주석을 달며 raw span+타이포 토큰을 재작성해 왔다 — 부품을 안 쓴 게 아니라 **부품에 자리가 없어서** 생긴 반복이라 개별 부품을 고쳐선 안 없어진다. `Text.truncate?: boolean`(닫힌 값·경쟁 경로 없음·기본 false) 승격 후보. **결정 대기.**

**모바일 게시판 작성 화면 개선 2건 (실화면 지적 — 조사 기반).**
1. **본문이 한 줄로 시작했다.** 회귀는 아니었다(데모도 같은 `<Textarea autosize/>`였다) — 처음부터 틀린 렌더였다. M3는 텍스트 영역을 텍스트 필드와 *다른 물건*으로 규정하며 **"큰 초기 크기가 긴 응답이 가능하고 권장됨을 알린다"**고 못박는데, 본문칸이 제목칸과 같은 높이면 그 신호가 없다. → **`Textarea.variant: 'field' | 'canvas'`** 신설(canvas=6줄에서 시작·항상 autosize). `minRows`는 여전히 안 연다 — 열면 소비처마다 본문 높이가 갈린다. **닫힌 두 어휘 중 고르게 하고 줄 수는 부품이 정한다.**
   - 기각한 안: `MobileBoardWrite`가 자기 본문칸에 CSS로 min-height를 먹이는 것 — 부품 내부를 바깥에서 덮는 짓이고 같은 실수를 DecisionPanel에서 이미 교정했다.
2. **수신자가 본문 자리를 먹었다.** 칩 줄+빠른추가+조직도가 항상 펼쳐져 약 200px을 차지해, 폰 첫 화면에 본문이 거의 안 들어왔다. → **접힌 요약 한 줄**(`인사팀 외 2 ⌄`, 44px)로 바꾸고 탭하면 그 자리에서 펼친다.
   - 반론을 반영한 지점: 모바일 폼에서 접기는 *"두 번 탭 + 옵션이 숨는다"*는 경고를 받는다(Smashing). 그 경고는 **값까지 숨겼을 때** 적중하므로, 값(누가 받는지)은 접힌 줄에 그대로 두고 **고르는 도구만** 숨겼다. 펼침 안에서는 접기를 한 겹 더 두지 않는다(예전엔 조직도가 또 접혀 두 번 탭이었다 — 두 토글을 하나로 폈다).
   - '수신자 N명' 표기는 삭제 — '외 N'이 이미 말한다(중복 신호).

**남은 것(작성 화면):** ① 첨부 행에 파일 크기 표시 ② `accept?: 'all'|'image'|'document'` 닫힌 프리셋 ③ 순서 재배치(본문 다음 첨부·게시옵션) — 셋 다 이번 지적의 B·D안으로 승인 대기.

**실화면 검증에서 재설계한 것 (같은 작업 내 — 모바일 폼의 시각 체계).** 3부품을 올린 뒤 글쓰기 화면을 보니 **데스크탑 폼을 그대로 옮겨놓은 상태**였다. 지적을 받고 조사부터 다시 했고, 그 과정에서 내 가정 하나가 뒤집혔다.

- **가정 기각: "iOS 설정처럼 좌측 라벨 행"** — Baymard는 모바일에서 inline(좌측) 라벨을 *쓰지 말라*고 못박는다(좁은 폭에서 입력칸이 쪼그라들고 오류가 는다). 상단 라벨이 완료 시간을 최대 50% 줄인다는 아이트래킹(Wroblewski)이 NN·Baymard 공통 권고다. **라벨 위치는 원래가 맞았다.**
- **진짜 결함은 어포던스였다.** iOS grouped list가 성립하는 건 *행*이 경계를 갖기 때문인데, 나는 상자만 벗기고 행을 안 줘서 값이 그냥 글자로 떠 있었다. → **`MobileField` 신설(밑줄 필드)**: [작은 라벨]/[값]/[아래 헤어라인]. 포커스·에러를 **밑줄 색**으로 말한다(아웃라인 상자를 쓰면 벗긴 상자가 포커스 때만 되살아난다). 모바일에서 데스크탑 `FormField`는 더 이상 쓰지 않는다.
- **필드 크롬은 셸 스코프가 재선언한다** — `.ms { --field-border: transparent }` + Mantine 입력 padding/배경. `--input-height-*`를 덮어 44pt를 만든 것과 같은 통로라 **부품은 한 줄도 안 고쳤고**, 한 곳이 바뀌면 모바일 폼 전부가 따라온다. 윤곽은 *지우지* 않고 **투명하게** 둬서 FormField의 에러 경로(`--field-border` → danger)가 그대로 산다. Mantine 내부에 닿는 **명시 예외**이며 `mobileshell.css` 한 파일에 가뒀다.
- **`MobileChoice` 신설(가로 스크롤 칩 줄)** — 분류처럼 선택지가 몇 개뿐이면 Select는 (1)열고 (2)고르는 두 동작 + 오버레이다. 더 중요한 건 **신호 분리**: 드롭다운(오버레이)과 인라인 펼침(수신자)이 같은 꺽쇠를 쓰고 있어 **화면이 거짓말을 하고 있었다**. 분류를 칩으로 바꿔 꺽쇠를 *펼침*에만 남겼다. 게시판 목록의 말머리 필터가 쓰던 칩 줄과 **같은 부품**으로 합쳤다(필터냐 폼 값이냐는 데이터의 차이지 컨트롤의 차이가 아니다).
- **`Textarea.variant: 'field' | 'canvas'`** — 본문칸이 제목칸과 같은 한 줄로 시작해 M3가 못박은 "큰 초기 크기 = 긴 응답이 가능·권장됨"의 신호가 없었다. canvas=6줄에서 시작·항상 autosize. `minRows`는 여전히 안 연다(열면 소비처마다 본문 높이가 갈린다).
- **`MobileListRow.emphasis`** — 안 읽은 행을 굵기로. 색이 아닌 이유는 폰 목록이 배지로 이미 붐벼 색끼리 싸우기 때문.
- **`MobileSection` 2건**: ① 내용이 없으면 **본문 div를 안 그린다**(첨부 0건이 빈 여백 블록을 남겼다) ② **액션이 있는 헤더는 대칭 행**이 된다 — 캡션 헤더의 여백은 위 lg(24)/아래 xs(8)로 *일부러* 비대칭인데(자기 본문에 붙으라고) 거기 44px 컨트롤이 들어가 위18/아래9로 어긋났다(실측 지적).
- **더보기는 데이터가 결정한다** — `onLoadMore`만 보고 그리던 것을 `posts.length < totalCount`로. 총 4건에 4건이 다 보이는데 더보기가 있으면 없는 걸 있다고 말하는 셈이다(데스크탑이 `totalPages > 1`일 때만 Pagination을 그리는 규율과 같다).
- **임시저장을 부품에서 뺐다** — 등록과 같은 위계가 아니다. 등록은 *커밋*, 임시저장은 *안전망*이라 업계 권고는 ① 백그라운드 자동 저장 ② 이탈 시점 확인 ③ *눈에 안 띄는* 명시 버튼("아예 없애면 불안을 만든다")이고, 그 자리는 셸 Navigation 우측이다. 폼 끝은 정작 나가려는 순간 화면 밖이라 최악이었다.
- **dev 박물관 대분류** — `데스크탑(106) / 모바일(16)`. 가르는 기준은 `Mobile*` 접두 하나(이미 문서화된 경계)라 수동 목록이 없고 부품이 늘어도 분류가 따라온다.
