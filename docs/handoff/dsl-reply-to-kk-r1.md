## §1 형태가 바뀌는 것 — 회신 필요

### 1-1. 2-2 `MobileTaskList` → **`MobileGroupedList`** + `status`

**이름**: `Task`는 도메인 이름이다(06 §5 "도메인 이름을 붙인 모든 것"을 안 만든다).
이 부품이 실제로 하는 일은 "섹션·그룹이 있는 목록"이라 그대로 부른다.
2-1과의 관계도 이름에서 드러난다 — 평면(`MobileList`) / 그룹(`MobileGroupedList`).

**`status` 누락**: 스키마에 로딩·빈 상태가 없다. 그대로 만들면 **2-1이 세운 로딩 규율이 또 갈린다**
(v0.68.0: 400ms 지연 스피너 · 이미 행이 있으면 지우지 않음). 2-1과 **같은 `status` 계약**을 받는다.

> 2-1이 지적한 문제("로딩 규율이 게시판에만 적용")를 2-2가 그대로 반복하게 된다. 같은 이유로 막는다.

### 1-2. 2-3 `MobileActionRow` → **`MobileListRow.actions`**

제약 진단은 정확하다(`onClick`이 루트를 `<button>`으로 만들어 `trailing`에 버튼을 못 넣는다).
다만 **그 문제는 v0.67.0에서 이미 풀렸다** — `MobileFileRow.onOpen`이 같은 상황이었고,
`data-split`일 때 행을 컨테이너로 바꾸고 [본체 버튼 | 우측 버튼]을 형제로 둔다.

```ts
// MobileListRow에 추가
actions?: readonly [Action] | readonly [Action, Action];
// actions가 있으면 루트가 div, 본문이 button, 액션이 형제 button — 히트 영역이 갈린다
```

새 부품 대신 이걸 쓰면 부품이 하나 줄고 두 행 부품이 같은 기제·같은 CSS를 쓴다.
`selectable`(일괄)과 `actions`(그 자리)의 구분은 kk 설명 그대로다.

**부품 이름으로 노출되길 원하는 이유가 있으면 알려달라** — 없으면 이대로 간다.

### 1-3. 2-4 `FilterMarker.swatch.color: string` — 닫힌 값으로

자유 색 문자열은 헌법 5(열린 스칼라 금지) 위반이라 그대로는 못 받는다.

```ts
// 요청안
| { kind: 'swatch'; color: BadgeColor }   // 'neutral'|'success'|'warning'|'danger'|'info'
```

**kk 구현본이 실제로 어떤 색을 쓰는지 알려달라.** 도메인 색이 6개를 넘거나 임의 hex라면
그건 색이 아니라 *구분자*라는 뜻이므로 `initial`(글자)로 대체하는 편이 맞을 수 있다.

### 1-4. 2-6 `MobileBulkBar` — 기각. 이미 있다

`selectedCount` + `actions` + `onCancel`은 **`MobileDecisionBar`(v0.66.0)로 그대로 조립된다.**
우리 데모가 이미 그 형태다:

```tsx
bottom={<MobileDecisionBar
  primary={{ label: `${sel.length}건 승인`, onClick: run }}
  more={[{ label: '선택 해제', onClick: clear }]} />}
```
취소(모드 종료)는 셸 상단 `onBack`이 받는다 — 하단에 또 두면 탈출구가 둘이 된다.

**진짜 요청은 바가 아니라 `BulkReport`다.** kk도 *"부품이 아니라 규율"* 이라 적었고 동의한다.
그건 하단 바의 일이 아니라 **알림**의 일이라 기존 토스트로 받고, 문구 규칙(3건 나열 + `외 N건`)만
공유 헬퍼로 낸다. **부품을 만들지 않는다.**

## §2 §4 논쟁 — kk가 맞다

칩 줄을 안 낸다. 근거는 kk의 실패 경험이 맞아서가 아니라 **두 물건이 다르기 때문**이다:

- 조사가 수렴으로 본 것(Jira·Drive·ClickUp·Asana) = **활성 필터를 *보여주는* 칩**
- kk 요구(2-4) = **필터를 *고르는* 컨트롤**

§4에서 kk가 "배타적이지 않다"고 짚은 게 정확하다. 우리도 그렇게 본다.

**참고**: 우리는 2026-08-04 판정에서 `MobileFilterChips`·`MobilePropertyChips`를
**"소비처가 없어서 안 만든다"** 로 닫았다(06 §7). 이제 소비처가 왔는데 요구가 칩이 아니라 축 바다.
→ 칩 줄은 계속 안 만든다. 나중에 "활성 필터를 보여줄" 요구가 따로 오면 그때 연다.

## §3 넘겨달라 — 구현본

**필수 3건** — 동작 계약이 촘촘해 검증된 코드를 보고 시작하는 편이 빠르다.

| | 이유 |
|---|---|
| **2-4 `MobileFilterBar` (195줄)** | 메뉴 위치·요약 말줄임·축 간 키 충돌 방지의 실제 처리 |
| **2-5 `MobileShell.profile` (330줄)** | 기기 분기(팝오버/드로어)의 실제 형태 |
| **3-6 `MobilePullToRefresh` (130줄)** | `preventDefault` 조건이 까다롭다. 잘못 쓰면 다른 제스처를 먹는다 |

**있으면 좋음 2건** — 스키마만으로도 되지만 참고하겠다: 2-2(210줄) · 2-8(88줄).

**2-6은 안 받는다**(기각). 다만 실패 보고 문구를 만드는 부분만 짧게 발췌해주면 헬퍼에 반영한다.

**그리고 포크 중인 것들의 diff** — 3-2 `MobileDisclosure`, 3-3~3-5 `MobileCalendar`.
포크에서 무엇을 고쳤는지가 곧 요구 명세다. 스키마보다 정확하다.

## §4 확인 필요 — 설계에 걸리는 것

### 4-1. 2-1의 `filters`와 2-4 `MobileFilterBar`의 관계

§5 점검표에서 목록 ①이 *"축 2 · `MobileChoice`"* 인데, 2-4도 축 단위 필터다.
**한 화면에 칩 줄과 축 바가 같이 서는가, 아니면 화면마다 하나만 쓰는가?**
같이 선다면 둘의 역할 경계를 계약에 적어야 한다(안 그러면 소비처마다 갈린다).

### 4-2. 2-3 행 액션의 실제 개수

상한을 2로 잡았다(`[Action] | [Action, Action]`). 06 §4가 인라인 3을 상한으로 두지만,
**행 안에서는 2가 실질 상한**이라고 본다(제목·메타가 이미 폭을 쓰므로).
**3개가 필요한 행이 실제로 있는지** 알려달라. 있으면 상한을 다시 본다.

### 4-3. 2-5 profile의 기기 분기

*"포인터=팝오버 / 터치=드로어"* 라 했는데, **`MobileShell`을 태블릿에서도 쓰는가?**
우리 규율은 768 단일 분기이고 그 아래는 전부 `MobileShell`이다. 모바일 셸 안이면 항상 터치이므로
**드로어 하나로 고정**하려 한다 — 포인터 분기를 여기서 새로 열 이유가 없다면.

### 4-4. §5 BottomSheet — 폼 필드의 실제 구성

"3~4개 필드"라 했는데 **어떤 타입인지** 알려달라(텍스트·금액·날짜·선택).
키보드 회피 처리가 필드 타입에 따라 갈린다(날짜 피커는 키보드를 안 띄운다).
06 §2-2 상한(입력 6개 넘으면 시트가 아니라 페이지)에는 여유 있게 들어간다.

### 4-5. 3-4 연속 구간 라벨 반복 — 기본값

prop으로 열어달라 했는데 **기본값을 어디로 둘지**가 남는다.
데스크탑이 이미 반복하므로 **기본을 반복으로** 두는 게 두 표현을 맞추는 길이라 본다.
그러면 kk는 prop을 안 줘도 된다. 이견 있으면 알려달라.

### 4-6. 2-8 적용 표의 실제 열 구성

≈9열이라 했는데 **카드에서 무엇을 버리는지**가 계약의 본체다.
`RecordRow`가 `cells`(표) 와 `title`/`badges`/`meta`/`trailing`(카드)을 따로 받는 형태인데,
그러면 kk가 매핑을 두 번 쓰게 되어 §2-8이 지적한 사고(한쪽에만 강조가 걸림)가 다시 난다.
**열 목록과 카드에서 살릴 것을 주면** 파생 규칙을 부품이 갖도록 설계하겠다.
