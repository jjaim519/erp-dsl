## 3. 이 이행에서 배운 작업 규율 (다음 세션에 그대로 적용할 것)

1. **breaking에 모아두기 전에 정말 breaking인지 확인한다.**
   R4에 모아둔 5건 중 실제 breaking은 하나였다. `Chip.type`을 R2에서 R4로 미룬 판단이 틀렸고,
   그동안 `MobileChoice`가 거짓 시맨틱을 한 릴리스 더 달고 있었다.
2. **주석으로 적힌 상한은 지켜지지 않는다 — 타입/구조에 박는다.**
   `MobileShell.actions` 튜플, `MobileDecisionBar.primary` 단수가 그 적용례다.
3. **셸 스코프 규칙을 바꾸면 파급 범위 전체를 훑는다.**
   R1에서 `.ms` 입력칸 규칙 하나를 바꿔 `InputGroup`(검색칸)을 깼는데, 작성 화면만 확인하라고 안내해
   사용자가 스크린샷으로 먼저 발견했다. `controls.css`의 `!important` 3줄이 원인이었다.
4. **근거의 *등급*을 먼저 본다.** 캔버스에 포커스 상자를 남긴 근거가 WCAG 2.4.13이었는데 그건 **AAA**다.
   기준선인 2.4.7(AA)은 캐럿을 포커스 표시로 인정한다.
5. **시각 판단을 물을 때는 목업을 그린다.** 텍스트 설명으로 "어느 쪽이 나은가"를 물으면 답할 수 없다.
6. **보고에는 "사용자가 할 액션"을 경로·볼 것·통과 기준 3열로 적는다.**

## 4. R7 착수 지점 — T2 부품군

조사(`mobile-research-2026-08.md` §8)의 T2 목록이 그대로 남아 있다. 우선순위 순:

| 후보 | 근거·요구 | 주의 |
|---|---|---|
| **BottomSheet** | **콘텐츠 시트만**(확정). 액션 목록 시트는 만들지 않는다 | 06 §2-2 — 중첩 금지, 입력 6개 넘으면 페이지 |
| **`MobilePropertyChips`** | 가장 강한 부품화 후보. Linear·ClickUp·Jira·Trello 수렴: 담당자→아바타만, 우선순위→글리프만, 라벨→`N labels`, **필드명 없음**, 미설정은 흐린 칩, trailing `+` 고정 | `MobileChoice`(값 선택)와 경계를 그어야 한다 |
| **`MobileFilterChips`** | 활성 필터 가로 스크롤 + 끝에 Clear(Jira·Drive·ClickUp·Asana) | 위와 형태가 같다 — **셋이 정말 다른 물건인지 먼저 판정**(rule of three) |
| **TableRow**(라벨-값 행) | `DescriptionList`의 모바일 짝. TDS `TableRow(align, leftRatio)` | 06 §3-4 — 폰에 표를 놓지 않는다는 규율과의 관계를 정리 |
| **ListFooter** | '더보기'의 부품화. TDS는 `border: full\|indented\|none`까지 닫음 | 지금은 `MobileBoardList` 안에 인라인 |
| 모바일 스켈레톤·빈 상태 | `MobileBoardList`가 데스크탑 `EmptyState`를 그대로 쓴다(모바일 빈 상태 어휘 없음) | |

**착수 전 판정할 것**: 위 칩 계열 3종(`MobileChoice` · PropertyChips · FilterChips)이 정말 다른 부품인지.
형태가 같으면 하나로 모으는 게 규율이다(`MobileChoice` 헤더가 이미 필터와 폼 값을 그렇게 합쳤다).
**옵션으로 얹지 말고, 축이 추가될 때만 연다**(06 §3-1).

## 5. 검증 동선 — /dev 하네스 (R1에서 새로 만듦)

```
npm run dev        # predev가 pdf.js 자산을 public/pdfjs 로 자동 복사
```

| 경로 | 무엇 |
|---|---|
| `/dev` → 모바일 → 부품 클릭 | **부품 하나가 폰 프레임(iframe)에 바로 뜬다.** 예전처럼 4탭 데모를 통과하지 않는다 |
| `/dev` → 모바일 → **화면** | 조립된 화면으로 직행(빈 상태 · 발주 탭 · 일정 상세 · 4탭 통합) |
| `/shell/m/part/<Name>` | 캔버스 실주소. iframe 없이 단독으로 열 수 있다 |
| `/dev` 좌측 `아주크게` | 폰트 스케일. **iframe 안에도 적용된다**(MutationObserver → `?fs=`) |

**단일 출처**: 모바일 라이브 예시는 `src/ui/_mobileDemos.tsx`, 데이터는 `src/ui/_devFixtures.ts`.
`_registry.tsx`에 모바일 링크를 되살리지 말 것 — 두 출처가 되는 순간 한쪽이 낡는다(그 자리에 주석으로 못박아뒀다).
새 부품을 만들면 **상태를 나란히 놓은 데모**를 추가한다(조작해야만 보이는 상태를 만들지 않는다).

## 6. 열려 있는 것

### 6-1. kk 회신 대기 2건 — `docs/handoff/mobile-reply-to-kk.md` §5

1. **한글 PDF 실물 확인.** `cmaps` 배선이 맞았는지의 **유일한 증거**다. 우리 dev 환경엔 실물 한글 PDF가
   없어 확인하지 못했다. 깨지면 `_pdfEngine.ts` 한 곳에서 고친다.
2. **게시판 '글쓰기' 위치.** `MobileTop.action`(우상단)에 뒀고 하단 FAB은 기각했다(06 §2-1).
   **뒤집힐 조건**: 네이버웍스·WEHAGO가 하단 FAB을 쓴다면 재고. 공식 문서로는 확인 실패했다.

### 6-2. 미답 판단 2건 (배포됨 — 실사용에서 보고 정하면 된다)

- **데스크탑 입력칸 윤곽 `--border-field` = `neutral[4]`(2.59:1)** — 3:1 의도적 미달. 무거우면 `neutral[3]`로.
- **모바일 입력칸 면 `--surface-input` = `neutral[1]`(1.09:1)** — 진하거나 흐리면 `neutral[0]`/`neutral[2]`로.

둘 다 `theme.ts` 한 줄이고 미달분은 고대비 모드(`a11y.css`)가 받는다.

### 6-3. 격하된 항목

**iOS 26 `blob:` iframe 검증** — 이전 인수인계가 "R6 착수 전 확인"으로 잡았으나 **결국 막지 않았다.**
pdf.js 경로가 전 플랫폼에서 동작하기 때문이다(Android는 네이티브가 아예 불가라 pdf.js가 유일한 길).
이제 "iOS에서 pdf.js를 건너뛰고 네이티브를 쓸 수 있나"라는 **최적화 질문**이다. 급하지 않다.

### 6-4. R4에서 미룬 것

`MobileListRow.selectable`/`selected`(일괄 처리) · 상태 칩 슬롯. **additive라 언제든 넣을 수 있다** —
소비처(결재함 일괄 승인)가 생길 때 넣는다. 지금 만들면 쓰는 데 없는 API가 된다.
