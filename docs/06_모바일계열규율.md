# 06. 모바일 계열 규율 (무엇을 지키고 무엇을 안 만드는가)

> 본 문서는 **규율 선언문**이다. 서술이 아니라 인용되기 위해 있다 — 부품 주석·리뷰·회신 문서가 여기 조항 번호를 가리킨다.
> 근거의 원문 요약은 「docs/handoff/mobile-research-2026-08.md」(6개 라인 전수 조사)에 있다. 본 문서는 그 조사가 **확정한 것만** 옮긴다.
> 범위: `Mobile*` 접두를 가진 모든 부품 + 그 아래 전역 층. 데스크탑 계열은 「01」·「05」를 따른다.

---

## 0. 구조

규율은 **전역 층(§1) + 3축(§2~4)** 두 겹이다.

- **전역 층**은 소비처가 고를 수 없다. 그냥 깔린다. 축이 없다.
- **3축**은 부품이 소비처에게 하는 약속을 가르는 언어다. 모든 부품 규율은 셋 중 하나에 속한다.

> 조사가 확정한 규율 19건을 이 격자에 전수 배치했을 때, 4건이 어느 축에도 안 들어갔다.
> 그 4건이 전부 전역 층이었다 — 그래서 축을 넷으로 늘리지 않고 층을 하나 더 팠다.

---

## 1. 전역 층 (L0)

부품이 하나도 아닌데 파급이 가장 크다. **부품 작업보다 먼저 깐다.**

### 1-1. `word-break: keep-all` 전역

한글은 음절 단위로 끊기면 안 된다. 리셋에 깔고 **예외를 유틸로 연다**(`.break-all` — URL·코드·ID용).
근거: KRDS가 정확히 이 구조(리셋 + 예외 유틸)를 쓴다.

### 1-2. 폰트 스케일 — px 폰트 금지

`src/ui/fontscale.css`가 루트 `font-size`를 112.5%/125%로 올린다. **px 리터럴은 이 배율을 안 탄다.**

- 부품 CSS에서 **폰트 크기를 px로 쓰지 않는다.** 토큰(`--typo-*`) 또는 rem/em만.
- 스케일을 타면 안 되는 것(터치타깃 하한, 헤어라인 굵기, 아이콘 박스)은 px로 두되 **주석으로 이유를 남긴다.**
- 검증: `/dev` 좌측 `기존 / 크게 / 아주크게` 토글.

### 1-3. 입력 필드 경계 — 역할을 가르고, 3:1은 고대비 모드가 받는다

**입력칸 경계는 구분선과 다른 역할이다.** 전에는 같은 값(`--border-default`)을 빌려 써서 입력칸이 섹션
헤어라인과 같은 색이었다 — 라이트 **1.27:1**, 칸과 선이 구분되지 않았다.

| 역할 토큰 | 값(light) | 대비 | 용도 |
|---|---|---|---|
| `--border-default` | `neutral[2]` | 1.27:1 | 구분선·헤어라인. **3:1 대상 아님 — 건드리지 않는다**(164곳) |
| `--border-field` | `neutral[4]` | **2.59:1** | 데스크탑 입력칸 윤곽. **의도적 미달** |
| `--surface-input` | `neutral[1]` | **1.09:1** | 모바일 입력칸 면. **의도적 미달** |
| `--border-field-strong` | `neutral[6]` | 7.60:1 | **고대비 모드 전용** |

**두 기본값이 3:1에 미달하는 것은 사고가 아니라 결정이다.**

- 근거: KRDS 원문은 *"입력 필드의 **테두리 또는 채움 색상**이 인접 배경과 3:1 이상 &hellip; **권장**합니다"* —
  채움도 인정 대상이고, 필수가 아니라 권장이다.
- 3:1 단(`neutral[5]`)은 데스크탑 폼에서 과하게 무겁고, 모바일에서 3:1을 만족하는 면은 iOS·M3 어휘를 벗어난다.
- 미달분은 **`a11y.css`의 `prefers-contrast: more` / `forced-colors: active`가 받는다** — 사용자가
  고대비를 요청하면 윤곽이 `--border-field-strong`으로 켜진다.

> `--border-default`를 진하게 올려 해결하려 들지 말 것. 데스크탑 전 부품의 구분선까지 같이 바뀐다.
> **포커스는 별개다** — `--border-focus`는 10.08:1로 WCAG 2.4.13을 여유롭게 통과한다(§3-3).

### 1-4. 제스처는 가속기이지 유일 경로가 아니다

스와이프로만 닿는 기능을 만들지 않는다. **모든 스와이프 액션은 탭으로도 닿아야 한다.**
근거: SAP Fiori·ServiceNow가 각자 접근성 의무로 명문화. ServiceNow가 iOS에서 스와이프 전용으로 낸 건은 불일치(버그)로 KB 등록됐다.

### 1-5. 뷰포트 분기는 768 한 곳

하한 `48em`(768). 새 임계값을 들이지 않는다 — 셸과 부품이 어긋나는 폭 구간이 생긴다.
`em` 기준이므로 폰트 스케일과 무관하다(`AppShell.tsx:56`).

## 2. 축 A — 화면 유형이 하단을 가른다

"모바일은 하단 고정"이 아니다. **커밋이 목적인 화면만 하단을 쓴다.**

| | 조회·탐색 화면 | 커밋 화면 |
|---|---|---|
| 하단 | 내비게이션에 양보 | `MobileShell.bottom` 고정 |
| 저장 | 해당 없음 | 2단 커밋(결정 → 선택 코멘트 → 확정) |
| 강조 버튼 | 0개 | **페이지당 1개** |
| 진입 | 전체화면 push | 전체화면 push |
| 예 | 목록·상세·검색·캘린더 | 작성·결재·승인·신청 |

**판정은 한 문장으로 한다: 이 화면에 &ldquo;확정&rdquo; 버튼이 있는가.**
협업 도구가 하단을 안 쓰는 이유는 문화가 아니라 tap-in-place + 자동 저장이라 **고정할 그 버튼이 없기 때문**이다.

### 2-1. 생성 진입은 하단이다

`MobileTop.action`은 오버플로(복사·보관·설정)를 받는다. **'글쓰기' 같은 생성 진입을 받지 않는다.**
오버플로와 진입은 다른 물건이다 — Google·Trello·Monday·ClickUp·Asana 전부 생성은 하단이다.

### 2-2. 시트는 생성·편집·피커에만

기본은 전체화면 push. **시트 중첩 금지**(만장일치). 입력이 6개를 넘으면 시트가 아니라 페이지다.
액션 목록 시트(버튼만 든 시트)는 **만들지 않는다** — 액션 목록은 `Menu`다.

### 2-3. 하단을 정당화하는 것은 위치 불변성이다

도달성이 아니다(NN/g가 도달성 논거를 반박). 결재를 연속으로 처리할 때 **문서 길이가 제각각이어도 버튼이 매번 같은 자리**에 있는 것이 실익이다.

## 3. 축 B — 표현은 닫힌 열거로 선언한다

한 부품이 변신하되, **결과를 소비처가 닫힌 enum으로 선언한다.**
선례: Primer `position` · Spectrum `mobileType` · Polaris `listSlot` · TDS `TextField variant` · Basecamp `presentation`. 우리 `ObjectCard` 역할 슬롯이 같은 형태다.

### 3-1. 열거를 여는 조건

**축이 하나 추가될 때만 연다. 옵션이 하나 추가될 때는 안 연다.**
이 구분이 「01」의 옵션 스태킹 금지와 충돌하지 않는 유일한 근거다.

### 3-2. 부착 지점 — 칸이 아니라 원자

면·윤곽은 **입력 원자**(`TextInput`·`Textarea`·`Select`)에 붙인다. **칸(`MobileField`)에 붙이지 않는다.**

칸에 붙이면 즉시 반례가 나온다 — `MobileBoardWrite` 3칸 실측:

| 칸 | 칸 안에 든 것 | 면·윤곽을 입힐 수 있나 |
|---|---|---|
| 분류 | `MobileChoice` 칩 줄(칩마다 pill 윤곽 + 좌우 스크롤) | 불가 — 윤곽 2중, 상자가 없는 끝을 그린다 |
| 제목 | `TextInput` | 가능 |
| 수신자 | 펼침 트리거 + 같은 칸에서 열리는 조직도 트리 | 접힘만 — 펼치면 상자가 트리를 삼키거나 트리가 상자를 뚫는다 |

**밑줄은 칸 단위로 성립하고, 면·윤곽은 원자 단위로만 성립한다.** 이 비대칭이 부착 지점을 정한다.

부작용이 하나 있고, 그게 오히려 이점이다 — **칩 줄·펼침 트리거는 통로를 안 읽으므로 자동으로 제외된다.**
규율을 코드가 막는 것이 아니라 구조가 이미 그렇다.

### 3-3. 폼 어휘 — 면(fill) + 포커스 윤곽

**모바일 입력칸은 채워진 라운드 박스다.** 밑줄도 상시 윤곽도 아니다.

| 상태 | 표현 | 값 |
|---|---|---|
| 기본 | 면만 | `--surface-input`, `radius.md 16` + squircle, 윤곽 2px **투명** |
| 포커스 | 윤곽 2px | `--border-focus` (10.08:1) |
| 에러 | 윤곽 2px | `--text-danger` — **포커스보다 세다** |
| 고대비 | 윤곽 상시 | `--border-field-strong` (§1-3) |

근거 3층:

1. **정본** — M3 filled가 container(면) + active indicator(선)로 역할을 나눈다. 면이 "쓸 수 있는 자리"를,
   선이 상태를 말한다. M3는 indicator를 1dp→2dp로 굵히는데, 우리는 선을 상시 노출하지 않고 포커스·에러에서만 켠다.
2. **접근성** — WCAG 2.4.13: 채움만 있고 테두리 없는 입력의 포커스는 ① 안쪽 표시자 또는 ② **테두리**로
   표시하고 최소 2px·상태 간 3:1을 만족해야 한다. **②를 택했다.**
3. **레포** — `theme.ts`가 이미 `corner-shape: superellipse(2)` + `radius.md 16`을 깔아뒀다
   ("squircle 곡률이 보이려면 큰 반경 필요"). **밑줄 어휘는 이 토큰을 쓸 수 없다** — 곡률이 드러날 면이 없다.

> 윤곽 자리(2px)는 평소에도 **투명으로 잡아둔다** — 포커스 때 칸 높이가 안 흔들린다.
> 구현은 `border-color` 직접 지정이 아니라 **`--field-border` 역할 변수를 덮는 방식**이어야 한다:
> `fieldBorder`(`_fieldStyles.ts`)가 Mantine `styles` prop을 타고 **인라인 스타일**이 되므로 CSS가 못 이긴다.

**철회된 안**: `variant: 'line' | 'box'` enum. 원자 3칸 중 실제로 윤곽을 입을 수 있는 게 1칸뿐이라
(§3-2) 전환해도 한 폼에 두 어휘가 남는다. **축이 추가되지 않았으므로 enum을 열지 않는다**(§3-1).

### 3-4. 폰에 표를 놓지 않는다

전자결재·레코드 계열은 진영 B다. 가로 스크롤 표를 만들지 않는다.
컬럼을 한 번 선언하고 **그 컬럼이 리스트 기하에서 갖는 역할을 닫힌 enum으로 선언**한다(Polaris `s-table` `listSlot` 형태).
복잡한 장표는 폰에서 재현하지 않고 **PDF로 렌더**한다 — 네이버웍스가 지출품의서에 쓰는 방식이다.

### 3-5. 색은 마지막 수단

숫자 배지 = 멘션급 에스컬레이션 전용. 일반 안읽음은 굵기/호이스트, 사용자 표시는 점.
근거: Teams·Google Chat·Slack 3사 독립 수렴.

## 4. 축 C — 능력 예산

**모바일은 데스크탑의 축소판이 아니라 형제 층이다.** 그 실천은 &ldquo;능력을 의도적으로 좁히는 것&rdquo;이고, 좁히는 정도는 숫자로 닫는다.

| 대상 | 예산 | 초과 시 |
|---|---|---|
| 인라인 액션 | **3** | 시트로 |
| 강조 버튼 | **페이지당 1** | 나머지는 보통 버튼 |
| 폼 필드 | 권장 **8** / 상한 **20** | 페이지 분할 |
| 칩 줄 선택지 | **5** | 드롭다운 재검토 |
| `MobileShell.actions` | **2** | 오버플로 메뉴 |
| 하단 탭 | **3~5** | 오버플로('더보기') 금지 |
| 시트 중첩 | **0** | — |

### 4-1. 편집 능력은 읽기 능력보다 좁다

Notion·Confluence·Basecamp 셋 다 명문화한 규율이다. 폰에서 못 하는 것을 결함으로 취급하지 않는다.
본문 서식이 필요한 글은 데스크탑에서 쓴다 — 매체가 다르면 작성 도구도 다르다.

### 4-2. 스와이프는 목록 트리아지 전용

문서·본문 안에서 스와이프를 쓰지 않는다. 메시지 버블 swipe-to-reply를 가져오지 않는다(메신저 3사 전부 없다).
그리고 §1-4에 걸린다 — 스와이프로만 닿는 것은 없다.

## 5. 만들지 않는 것

- **액션 목록 시트** — 액션 목록은 `Menu`다
- **문서 뷰어의 오피스·HWP 인라인 렌더** — 플랫폼·서버에 위임. 폴백 카드 + 내려받기
- **결재란 격자** — 폰에서는 트레일로
- **폰 일괄 승인 FAB**
- **`FieldGrid`의 모바일 짝** — PDF 폴백이 업계 선택
- **도메인 이름을 붙인 모든 것** — 결재·근태·휴가는 부품이 아니라 서식/스키마다(「01」 헌법 1번)

## 6. 철회된 근거

아래 인용은 **현행 정본에서 확인 실패했다.** 결론은 살아남고 근거만 바뀐다.

| 위치 | 철회 | 대체 |
|---|---|---|
| `MobileShell.tsx:9` · `MobileSection.tsx:4` | HIG가 inset grouped를 말린다 | **M3** — 여백·구분선으로 충분하면 카드를 쓰지 마라 / compact에서는 카드를 리스트로 |
| `MobileShell.tsx:14` | 탭 3~5는 HIG | **M3**(현행 HIG는 숫자를 안 박는다) |
| `mobilelist.css:48` | HIG 최소 터치타깃 44×44 | HIG는 **44 권장 / 28 하한** 2단. 단일 하한 **48dp는 M3** |
| `MobileComposer.tsx:3` | 하단 고정은 손이 닿기 때문 | **위치 불변성**(§2-3). NN/g가 도달성 논거를 반박 |
| `MobileField.tsx` 헤더 | 모바일은 밑줄 필드다 | **면(fill) 어휘**(§3-3). 밑줄만 쓰는 형태는 M3 filled에서 면만 뺀 것이었다 |
| 조사 §5 | KRDS는 박스형(윤곽)만 인정 | 원문은 **"테두리 또는 채움"** 이고 **권장**이다. 어휘 선택지가 2개가 아니라 5개였다 |

「모바일 = 형제 층」의 근거도 교체됐다: **Salt(JPMorgan)가 `touch` 밀도를 만들었다가 &ldquo;작은 화면에 최적화돼 있지 않다&rdquo;며 폐기**했다. 배수 스케일의 실패를 업계가 값으로 증명한 사례다.
